# 真实配置应用

Linux 托管内核启用且安装完成后，工作台显示“应用到内核”。默认 Windows 编辑环境继续使用模拟器。保存只持久化草稿；应用必须经过配置块摘要、增删行数和 YAML 差异预览，再点击确认。

## 配置事务

1. 请求绑定已保存草稿哈希、当前内核标识和预览时的已应用配置哈希。草稿冲突、陈旧内核或并发任务不会覆盖当前状态。一个任务锁串行处理内核更新、回退及配置应用。
2. 接受任务后冻结该份原文。浏览器断开不取消事务；应用期间另存的新草稿不会被误应用。客户端通过状态轮询确认结果，不把 HTTP 202 当作成功。
3. 检查 YAML 文档和当前托管边界，复制当前资源目录到候选目录，保存原始 YAML。配置中的注释、顺序和未知字段保持原样。
4. 使用当前真实内核执行 `mihomo -t`。版本和 Schema 文件先验证哈希；检查配置用独立副本，避免下载、解析资源时修改旧进程的缓存。失败时旧进程继续运行。
5. 校验通过，落盘记录切换意图，停止本管理器启动的进程，用候选原文及候选资源目录启动。
6. 连续检查进程存活、带密钥的 `/version`、`/configs` 返回的模式及代理端口、TCP 监听。端口被其他进程占用时不接管该进程。通过后才原子提交配置引用、应用时间、修订记录，并清除过时的待升级内核。
7. 启动或检查失败，停止候选，使用原配置及原资源目录恢复。失败草稿继续保留，已应用原文和成功历史不变。原配置也恢复失败时明确报告，不冒充运行正常。
8. 切换期间管理器被终止，重启时恢复最后提交的内核、配置和资源目录。配置第一次接入时记录原启动配置，但仍使用原进程的实际资源目录，不把校验失败误记成应用成功。

此流程使用重启切换，会短暂中断现有连接。检查保证本地核心配置及监听符合预期，不保证所有公网节点、DNS 上游或订阅长期可用。

## 配置与控制接口

`MIHOMO_CORE_CONFIG` 是初始配置和管理接口的部署输入。其 `external-controller` 必须为回环地址，secret 至少 16 字符。管理器通过 Mihomo 原生环境变量 `CLASH_OVERRIDE_EXTERNAL_CONTROLLER` 和 `CLASH_OVERRIDE_SECRET` 固定控制接口，不把密钥放入进程命令行，不改写用户 YAML。

草稿可以省略这两个字段；若显式填写，必须与管理服务一致，否则应用失败。清除继承的其他 `CLASH_*` 覆盖和命令钩子，防止它们绕过候选原文。

目前只支持回环显式代理：禁用 TUN、透明代理、allow-lan、自定义 listeners、tunnels 和附加控制监听。DNS 若监听，须为回环地址。provider 缓存使用配置资源目录内的相对路径，拒绝绝对路径和目录穿越，以确保候选不能写旧资源目录。绝大多数出站协议字段直接交给原生内核验证，不用前端有限 Schema 替代内核判断。

## 持久化

- 草稿与保存记录仍在 `.local/state.json`。默认模拟模式的已应用字段仅供模拟器使用。
- 实际配置在专属内核目录 `configurations/<随机标识>/config.yaml`，保留原始字节并记录哈希；资源目录为同级 `home/`。运行用 YAML 是从该原文产生的同字节副本。
- `core-state.json` 统一原子记录内核指针、配置指针、上一份配置、成功应用历史及切换状态。托管 `/api/state` 的 `applied` 和 `appliedRevision` 读取该指针对应的原文，不沿用模拟数据。
- 保存最多 30 份成功应用原文；只有当前和上一配置保留资源目录。清理仅处理专属目录内生成的标识，失败候选在任务结束后删除。首次启动资源目录保留作初始恢复来源。
- 内核升级和回退使用当前已应用原文；配置应用本身不改变内核版本或 Schema。

## API 与界面

`POST /api/apply` 在托管模式接受 `revision`、`expectedCurrent`、`expectedApplied`，返回 202 表示已接受。`GET /api/state` 提供真实已应用原文、哈希、历史及任务状态；失败不会改写草稿。预览后有其他页面完成应用，旧确认会被拒绝，需重新预览。

运行面板显示实际进程和已提交配置。临时运行模式、启停和节点选择仍未接入，托管模式的 `PATCH /api/runtime` 返回 409；不会偷偷调用模拟器。保存、放弃、取消预览流程仍可使用；应用失败显示持续错误说明，后端暂时不可达时显示结果待确认。
